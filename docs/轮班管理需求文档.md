# 轮班管理系统用户需求文档

**文档版本：** V1.0
**文档类型：** 用户需求文档（URD）
**系统名称：** 轮班管理系统
**核心排班制度：** 三八班倒
**文档状态：** 初稿

------

# 1. 项目概述

## 1.1 项目背景

部分生产、值班、运维等岗位采用固定的“三八班倒”工作制度。

三八班倒的基本循环为：

> 白班 → 夜班 → 休班 → 白班 → 夜班 → 休班……

传统情况下，工人通常通过纸质排班表、Excel 或人工通知查看自己的班次。

这种方式存在以下问题：

1. 排班信息分散。
2. 工人不方便随时查看自己的班次。
3. 排班周期需要人工计算。
4. 临时换班后，后续班次需要人工重新计算。
5. 容易出现排班错误。
6. 无法方便地查看历史调整记录。
7. 无法快速统计某段时间内的白班、夜班、休班和实际工作天数。
8. 手机查看体验较差。

因此，需要建设一个简单、直观、易使用的轮班管理系统。

------

# 2. 项目目标

系统主要解决以下问题：

> 只需要设置工人的排班起始日期和起始班次，系统即可自动计算后续三八班倒排班。

同时支持人工调整：

> 如果发生换班、调休等情况，可以手动修改某一天的班次，并根据实际需要选择是否从该日期开始重新计算后续班次。

系统最终实现：

```text
设置起始排班
      ↓
自动生成三八班
      ↓
手机查看每日班次
      ↓
临时换班
      ↓
重新计算后续班次
      ↓
查看历史
      ↓
统计工作情况
```

------

# 3. 用户角色

系统第一阶段主要包含两类用户。

## 3.1 普通工人

普通工人的主要需求是：

- 查看自己的班次。
- 查看今天上什么班。
- 查看明天和未来几天上什么班。
- 查看一段时间内的排班。
- 查看个人排班统计。
- 查看自己的排班调整情况。

普通工人原则上不能修改自己的排班，也不能查看其他工人的个人排班。

------

## 3.2 管理员

管理员负责系统中的排班管理。

主要需求：

- 管理工人。
- 设置工人的初始排班。
- 查看所有工人的排班。
- 调整工人的班次。
- 进行换班操作。
- 从指定日期重新计算后续排班。
- 查看排班调整历史。
- 查看排班统计。

------

# 4. 三八班倒业务规则

## 4.1 基础循环

系统默认使用以下循环：

```text
白班 → 夜班 → 休班 → 白班 → 夜班 → 休班……
```

例如：

| 日期       | 班次 |
| ---------- | ---- |
| 2026-09-01 | 白班 |
| 2026-09-02 | 夜班 |
| 2026-09-03 | 休班 |
| 2026-09-04 | 白班 |
| 2026-09-05 | 夜班 |
| 2026-09-06 | 休班 |

------

## 4.2 起始日期

每个工人需要设置一个排班起始日期。

例如：

```text
工人：张三
起始日期：2026-09-01
起始班次：白班
```

系统自动计算：

```text
9月1日  白班
9月2日  夜班
9月3日  休班
9月4日  白班
9月5日  夜班
9月6日  休班
……
```

------

## 4.3 起始班次

起始班次允许设置为：

- 白班
- 夜班
- 休班

例如：

如果设置：

```text
起始日期：9月1日
起始班次：夜班
```

则：

```text
9月1日  夜班
9月2日  休班
9月3日  白班
9月4日  夜班
……
```

如果设置：

```text
起始日期：9月1日
起始班次：休班
```

则：

```text
9月1日  休班
9月2日  白班
9月3日  夜班
9月4日  休班
……
```

# 5. 班次定义

系统第一阶段定义三种班次。

## 5.1 白班

名称：

> 白班

状态：

> 工作

具体工作时间需要根据实际使用单位配置。

------

## 5.2 夜班

名称：

> 夜班

状态：

> 工作

具体工作时间需要根据实际使用单位配置。

------

## 5.3 休班

名称：

> 休班

状态：

> 休息

休班不计入工作天数。

# 6. 工人管理

管理员可以管理工人基本信息。

## 6.1 工人信息

至少包含：

- 工人编号
- 姓名
- 所属部门
- 所属班组
- 排班开始日期
- 排班开始班次
- 当前状态

------

## 6.2 新增工人

管理员可以新增工人。

新增时需要填写：

```text
工号
姓名
部门
班组
排班开始日期
排班开始班次
```

保存后，系统自动建立该工人的三八班排班规则。

------

## 6.3 编辑工人

管理员可以修改：

- 姓名
- 工号
- 部门
- 班组
- 其他基本信息

涉及排班规则的修改必须明确提示管理员可能影响后续排班。

------

## 6.4 删除/停用工人

管理员可以停用工人。

停用后：

- 普通用户不能继续正常查看该工人的有效排班。
- 历史排班数据原则上保留。
- 历史调整记录原则上保留。

系统不应因为停用工人而直接删除历史数据。

# 7. 排班查看

系统必须提供直观的排班查看功能。

------

## 7.1 今日班次

用户进入系统后，应能够快速看到：

```text
今天
2026年9月25日

白班
```

同时可以显示：

```text
明天：夜班
后天：休班
```

让用户无需进入复杂页面就可以知道近期班次。

------

# 8. 排班日历

系统提供日历查看方式。

## 8.1 月历

用户可以选择月份。

例如：

```text

```

```text

     白  夜  休  白  夜  休

7    8   9  10  11  12  13
```

------

## 8.2 日期详情

点击某一天，可以查看：

```text

星期：星期五

班次：白班
状态：工作

排班来源：

```

如果当天经过人工调整，需要明确显示：

> 人工调整

------

# 9. 排班列表

除了月历模式，系统需要提供列表模式。

例如：

```text

白班

9月26日  星期六
夜班

9月27日  星期日
休班

9月28日  星期一
白班
```

用户可以在：

```text
月历
```

和：

```text
列表
```

之间切换。

------

# 10. 排班日期范围

用户可以查看指定时间范围内的排班。

例如：

```text
开始日期：2026-09-01
结束日期：2026-12-31
```

系统展示该时间范围内的完整排班。

不能限制用户只能查看当前月份。

------

# 11. 换班与排班调整

这是系统核心功能之一。

管理员可以对某一天的排班进行人工调整。

------

## 11.1 调整班次

例如：

原排班：

```text
9月25日 夜班
```

管理员可以修改为：

```text
白班
夜班
休班
```

------

# 12. 两种调整方式

系统必须明确区分两种调整方式。

------

## 12.1 仅修改当天

管理员选择：

> 仅修改当天

例如：

原排班：

```text
9月25日 夜班
9月26日 休班
9月27日 白班
9月28日 夜班
```

将9月25日改成白班。

结果：

```text
9月25日 白班 ← 修改
9月26日 休班
9月27日 白班
9月28日 夜班
```

只有指定日期发生变化。

后续基础排班不重新计算。

------

## 12.2 从当天开始重新排班

管理员选择：

> 从当天开始重新排班

例如原排班：

```text
9月25日 夜班
9月26日 休班
9月27日 白班
9月28日 夜班
9月29日 休班
```

管理员将9月25日调整为：

```text
休班
```

并选择：

> 从当天开始重新排班

那么从9月25日开始重新建立三八循环：

```text
9月25日 休班
9月26日 白班
9月27日 夜班
9月28日 休班
9月29日 白班
9月30日 夜班
……
```

也就是说：

> 调整日期本身作为新的排班周期起点。

------

# 13. 调整备注

管理员进行人工调整时，可以填写备注。

例如：

```text
备注：
与李四调班
```

或者：

```text
备注：
临时调休
```

备注用于后续查看调整原因。

------

# 14. 排班调整记录

系统需要保存排班调整历史。

至少记录：

- 调整时间
- 工人
- 调整日期
- 原班次
- 新班次
- 调整方式
- 调整备注
- 操作人

例如：

| 时间          | 工人 | 日期    | 原班次 | 新班次 | 类型           |
| ------------- | ---- | ------- | ------ | ------ | -------------- |
| 9月25日 08:30 | 张三 | 9月26日 | 夜班   | 休班   | 从当天重新排班 |

管理员可以查看历史记录。

------

# 15. 多次调整

系统必须支持同一个工人进行多次调整。

例如：

```text
第一次调整
9月10日重新排班

↓

第二次调整
9月20日重新排班

↓

第三次调整
9月28日重新排班
```

系统最终应该能够正确计算不同调整点之后的排班。

不能因为一次新的调整导致之前已经发生的排班记录丢失。

------

# 16. 排班统计

系统需要提供统计功能。

用户可以选择：

```text
工人
开始日期
结束日期
```

统计最终实际排班结果。

------

## 16.1 基础统计

例如：

```text
2026年9月

白班：10天
夜班：10天
休班：10天

工作天数：20天
休息天数：10天
```

其中：

```text
工作天数 = 白班 + 夜班
```

------

## 16.2 统计原则

统计必须基于：

> 最终实际排班结果

而不能简单按照原始三八循环计算。

例如某天经过人工调整，则统计应该按照调整后的最终班次计算。

# 23. 权限需求

## 23.1 普通工人

普通工人只能：

- 查看自己的排班。
- 查看自己的统计。
- 查看自己的排班调整信息。

普通工人不能：

- 查看其他工人的排班。
- 修改其他工人的排班。
- 修改系统排班规则。
- 查看管理员功能。

------

## 23.2 管理员

管理员可以：

- 管理工人。
- 查看工人排班。
- 创建排班。
- 调整排班。
- 查看历史记录。
- 查看统计。

------

# 24. 权限安全要求

权限控制必须由系统后端真正执行。

不能仅仅通过：

> 前端隐藏按钮

来实现权限控制。

即使普通用户直接访问管理接口，也必须被系统拒绝。

------

# 25. 数据准确性要求

系统必须保证：

> 同一个工人在同一个日期只能得到一个最终有效班次。

不能出现：

```text
9月25日
白班

同时又显示
夜班
```

等数据冲突。

------

# 26. 排班计算一致性

系统中所有地方看到的班次必须一致。

例如：

```text
首页
↓
今天：白班

排班日历
↓
9月25日：白班

排班列表
↓
9月25日：白班

统计
↓
白班 + 1
```

不能出现不同页面显示不同班次。

------

# 27. 数据保存

用户进行排班调整后：

1. 数据必须保存。
2. 刷新页面后不能恢复旧数据。
3. 重新登录后数据仍然存在。
4. 后续日期必须按照新的排班规则计算。
5. 历史调整记录必须保留。

------

# 28. 易用性要求

系统整体应保持简单。

目标用户不一定具备计算机专业知识。

因此：

- 页面不要过于复杂。
- 操作名称要直观。
- 避免使用难以理解的技术术语。
- 调整排班前明确提示影响范围。
- 删除、停用、重新排班等操作需要二次确认。
- 手机端按钮需要适合手指操作。

------

# 29. 错误提示

如果用户输入错误，需要给出明确提示。

例如：

```text
请选择排班开始日期
请选择起始班次
该工人已经存在排班规则
排班调整失败，请稍后重试
```

错误信息不能只显示：

```text
Error 500
```

等无法理解的技术信息。

# 33. 核心验收场景

系统完成后，至少需要验证以下场景。

## 场景一：基础排班

设置：

```text
9月1日 = 白班
```

系统应该得到：

```text
9月1日 白班
9月2日 夜班
9月3日 休班
9月4日 白班
9月5日 夜班
9月6日 休班
```

------

## 场景二：不同起始班次

测试：

```text
起始 = 白班
起始 = 夜班
起始 = 休班
```

三种情况都必须正确。

------

## 场景三：只修改当天

修改：

```text
9月10日
```

选择：

> 仅修改当天

要求：

> 只有9月10日发生变化，后续基础排班保持原来的三八循环。

------

## 场景四：重新排班

修改：

```text
9月10日
```

选择：

> 从当天开始重新排班

要求：

> 9月10日作为新的周期起点，后续按照新的班次重新计算。

------

## 场景五：多次调整

连续进行多次调整。

要求：

> 系统最终显示的每一天班次必须正确。

------

## 场景六：刷新

调整排班后：

```text
刷新页面
```

要求：

> 修改结果仍然存在。

------

## 场景七：手机端

使用手机访问系统：

```text
登录
↓
查看今天班次
↓
查看未来排班
↓
切换月历
↓
切换列表
↓
查看统计
```

要求：

> 全流程能够正常操作。

# 34. 非功能需求

## 34.1 易维护

系统应保持简单、清晰的结构。

第一阶段不要求：

- 微服务
- 分布式架构
- 大规模缓存
- 分库分表
- 复杂消息队列

优先保证：

> 稳定、简单、容易维护。

------

## 34.2 数据可靠性

排班数据和调整记录必须可靠保存。

不能因为刷新页面、重新登录导致数据丢失。

------

## 34.3 响应速度

普通排班查询应能够快速完成。

查看一个月的排班不应该出现明显等待。

# 37. 产品核心原则

整个系统围绕三个核心目标：

### 简单

管理员设置一次起始排班，系统自动计算。

### 直观

工人打开手机就能知道：

> 今天上什么班。

### 可调整

临时换班时：

> 手动修改一次，后面的班次自动按照新的规则计算。

最终用户体验应该接近：

```text
“告诉系统我从哪天开始上什么班，
系统帮我把后面的班全部算好；
临时换班，我改一下，
后面的班也自动跟着调整。”
```

------

# 38. 验收标准

当以下条件全部满足时，可以认为第一阶段基本完成：

-  可以创建工人。
-  可以设置起始日期。
-  可以设置起始班次。
-  系统可以自动计算三八班。
-  可以查看当天班次。
-  可以查看未来排班。
-  可以使用月历查看。
-  可以使用列表查看。
-  可以调整指定日期班次。
-  支持“仅修改当天”。
-  支持“从当天开始重新排班”。
-  后续班次能够正确更新。
-  可以查看调整历史。
-  可以统计白班、夜班、休班。
-  可以统计工作天数。
-  普通工人只能查看自己的排班。
-  管理员可以管理所有工人。
-  手机端可以正常使用。
-  PC端可以正常使用。
-  刷新页面后排班数据不会丢失。
-  重新登录后排班数据不会丢失。
-  核心排班逻辑经过实际测试。
-  不存在已知的核心业务错误。
